## 6. 版の上げ方

- 欄を**足す**(読み手が知らなくても動く)= `sap-feed/1` のまま。読み手は知らない欄を無視する。
- 欄を**消す・名前や型を変える・意味を変える**(例: 日付の書き方・`done` の意味)= `sap-feed/2` に上げる。読み手は知らない版で止まって画面に理由を出す(間違った束を黙って読まない)。
- 上げる時は ①この文書に新しい版の節を足す(古い版の節は残す) ②合成 Excel の道具と見出し一覧(`scripts/sap_synth/headers_spec.json`)は元の Excel の形の約束なので、束の版とは別に扱う ③読み手は直前の版を 1 つ前まで読めるようにするかをその時に決める(要確認)。

## 7. 決めた事(段2・11-24)と、まだ要確認

決めた(束を作る関数 `scripts/sap_feed/feed.py` に入っている・試験つき):
- 項目名は 2〜4 章の英名(`order`・`act`・`wc`・`std1` …)で確定(`sap-feed/1`)。理由: 設計 C-3 の日本語見出しは SAP 側の名前で、JSON のキーは別に持つ方が見出しが変わっても読み手が壊れない。
- 検査の `id` は設計の通し番号(①〜⑫)に、型の検査 `P1`(日付が文字・指図が数値セル・空など)を足した。理由: 設計 C-2 の ① は「見出しがあるか」だけで、型が違う物を止める検査が無かった。
- ⑧⑨⑩(件数・時間・作業区ごとの差)は、RPA の計算シート「工程_未完了」が合成では空なので、`.truth.json` の答え+別の数え方(辞書と Counter だけで数える別の経路)で代用する。`checks.notes` と各検査の `note` に代用した事を書く。本物で「工程_未完了」に行があれば行数も比べる(時間と作業区ごとは見出し不明のため行数だけ)。
- ⑨の時間は「単位が H の 標準値1+標準値2×数量」。単位が空・H でなく外した分と、作業区が空で外した行の分を足し戻して、参照(別の数え方・truth)と比べる(外した分は `info` に件数が出る)。
- ⑦ 実績の一番新しい日が基準日の 7 日以内。実績が 1 件も無い時も赤。⑫ の上限は 1,000,000 バイト(見本で約 850KB・案=要確認)。
- ② 行数の比べは、前回の記録(`sap-feed-record.json` の `rowCounts`)を渡した時だけ。初回は省略と書く。
- 束に入れる工程 = 終わっていない指図の工程すべて(済の工程も含む=前の工程の実績に使う)。作業区が空の行だけ「読めない行」として外し、理由別の件数を `dropped` に出す。
- 標準値が 3 つとも 0 の工程は `std1〜3` を全部 `null`(時間は不明・D5)。単位が H でない・空の値は `null`(D6)。
- 指図・活動・作業区が数値セルで入っている Excel は `P1` で止める(先頭の 0 が落ちている恐れがあり、元に戻せないため)。

まだ要確認(設計書に答えが無い):
- 「作業区」「作業区MT」「実績_週」「組立指図」「不足部品」「工程_未完了」シートの見出し(合成も本物の見出しが無いので読んでいない)。`wcMap`・`usualDays`・`issueDate` が空なのはこのため。
- `history.weekly` の「過去 12 週」の数え方が RPA の「実績_週」と同じか。
- 置き場(Firebase・社内・端末)は設計 F-2 の 1 の答え待ち。1 個 700KB 以下に割る時の分け方も未決(C-6)。

## 10. 束 machine(機械グループの画面用・11-24)

アプリの『機械グループ負荷』画面(sapGroups.js・sapProgress.js)は、検査以外の機械工程(旋盤・立旋盤・フライス・横M/C・門M/C・平面/円筒研削・歯切り・仕様変更・面取り洗浄)の未完了を全部使う。検査の作業区だけの 3 冊にも「どこにも使わない」件数にも入っていなかったので、4 冊目の束を足した。

- 中身: 工程の分類が `machine` か `wash` の物だけ。`misc`(付帯作業)と `inspect`(検査)は入れない。検査の作業区(app_wcs.json にある作業区)の工程は検査アプリの束が先で、machine には入れない(1 つの工程は 1 つの束だけ)。
- 分類の表: `scripts/sap_feed/machine_rules.json`(sapProgress.js の CODE_FALLBACK・NAME_RULES・readWorkName の規則を起こした設定)。feed.py の `classify_work` はこの表を読む。**sapProgress.js を直したらこの表も同じに直す**。同じ答えを返す事は `npm run sap-feed:test` が node で readWorkName を呼び、合成データの全工程+作業テキスト×作業区コードの 2,540 通りで確かめる。分類には SAP_作業 の「作業 Text」を使う(束には作業 Text そのものは入れない。入れるのは分類の結果 `name`・`kind` だけ)。「作業 Text」は読む必須の見出しに足した(検査①)。
- 束 machine の追加欄: `ops[].name`(機械グループの名前)・`ops[].kind`(`machine` か `wash`)・束の `app:"machine"`・`wcs`・`part`・`parts`。`ops[].suspectOrder` は machine の束には入れない(機械グループの画面は読まず、sapGroups.js が順番から自分で数えるため)。他の欄は src/domain/sapProgress.js の toStage が読む物を残した(order・act・wc・qty・std1〜3=hJ・hL・hN・done・actualEnd・earlyStart/earlyEnd=planStart/planEnd)。
- 大きさ: 1 冊が上限(1,000,000)を超える時は、**指図ごとに**割って `sap-feed-machine-1.json`・`sap-feed-machine-2.json` …とする(上限は変えない)。理由: 工程名(グループ)ごとに割ると、同じ指図の前後の工程が別の冊に分かれ、読み手(sapBoard.js・sapGroups.js の chainOf)が「1 つ前の工程の終わり」を引けなくなるため。指図ごとなら 1 つの指図の工程は必ず同じ冊に入る。読み手は全部の冊を足して読む(`parts` に冊の数)。`history.weekly` は 1 冊目だけに入れる(足して二重にならない)。
- 記録 `apps.machine`: 作業区・指図数・工程数・未完了数・バイト数・ハッシュ・`parts`(冊ごと)・`byName`(工程名ごとの件数)。`other` は machine に入れた分を引いた残り(本当にどこにも使わない工程)。
- 検査 A1 は machine を含めて保つ(和が全体と一致・重複 0・漏れは other に件数・machine に機械・洗浄以外が無い・history の重複なし)。
- 合成 3000 指図で machine は 2 冊(995,973 と 164,266 バイト)で、全部が上限以内。
