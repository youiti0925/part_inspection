## 接続契約（Claude担当）

既存の購読結果を渡してください。`SkillGrid` が受けるのは集計済み `model` だけです。
`lots` はシミュレーションの月・入荷範囲で絞る前の履歴を含む一覧、`workers` は休止中を含む全名簿です。

```jsx
import { SkillGrid, buildSkillGrid } from './opsim/skillGrid/index.js';

const skillGrid = useMemo(() => buildSkillGrid({
  lots, templates, workers,
  skills: settings?.skills,
  workerSkills: settings?.workerSkills,
  historyComplete: false, // アーカイブを含む全件受領を確認した時だけtrue
  sourceLabel: '呼ぶ側で確認した取得日・対象期間',
}), [lots, templates, workers, settings]);

<SkillGrid model={skillGrid} />
```

- 未受領は `null`、受領済み0件は `[]`。履歴の網羅性は既定で未確認。
- スキル名・0〜3の語彙は `domain/skillRegistry.js` を使用。必要スキル未設定と登録なしは区別。
- 表示は型式×テンプレ、またはテンプレ単位。工程行は作りません。
- 回数は完了ロットへの関与。同一ロットで同じ名前は何工程あっても1回。共同作業は各人1回。
- `tasks[].workerName`（辞書形式も可）を優先し、1件も無い時だけ `lot.workerId → workers.id.name` を補完。補完回数と由来を表示します。
- `SkillMap.computeSkillCounts` と同じ関与の意味です。ただし本表は「型式×テンプレ」で集計するため、作業者×スキルの既存集計値から逆算しません。共通スキル経由で別テンプレの回数を混ぜません。
- 入力の同一 `lot.id` は先勝ちで1回、重複数を警告。IDなしは入力1要素1ロットで警告。
- 同名・表記ゆれ・改名を推測で結合しません。0回の人・休止中・名簿外も残します。
- 登録ありはレベル1「教育中」を含み、部分登録は `1/2` のように表示。色を割付可否に読み替えないでください。
- 新規DB接続・読み書き・候補の足切り・優先順位計算はありません。

## 独立に見つけた注意点（既存側は変更していません）

1. ロット担当者からの補完は、実作業の証明ではありません。実績だけで「誰に渡せるか」を決めるには不足します。
2. ロット全体が未完了なら、中で完了済みの工程があってもこの回数には入りません。工程別の割付根拠と一致しない場合があります。
3. `computeSkillCounts` はロットに一部でも関与した人へ、そのテンプレの必要スキル全部を加算します。その回数は「そのスキルを実際に実施した回数」ではありません。
4. 必要スキル未設定・登録データ未受領・履歴の一部だけの読み込みは、力量の不足ではありません。0回や灰色を教育対象の自動判定に使わないでください。
5. 名前で結ぶ旧契約のため、同名や改名は個人の実績を誤って合わせる・分ける可能性があります。
6. 最終検査へ転用する時は、型式×templateIdだけで束ねず、`specialConditions` 相当の特注仕様をキーに加える検討が必要です。異なる仕様の実績を混ぜてはいけません。この製品検査版では特注仕様別の集計は実装していません。

この表だけでは「なぜ人が空くか」「どの教育なら渡せるか」は確定しません。
実作業者の根拠、先行工程の停止理由、現在の登録と結び付けるのは次の接続側の仕事です。
横並びの目的は各人の「回数／登録」の比較です。名簿が増えると横スクロールが必要になります。
作業者を勝手に隠さず、見たい型式・テンプレの検索で行を絞る構成です。多数列・拡大時の見やすさは実画面での確認が残っています。
